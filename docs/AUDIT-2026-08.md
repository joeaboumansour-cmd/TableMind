## P0 — Live exposure and live money bugs

### P0-1 🔴 API tenancy is an unsigned client-supplied header

Every data-bearing route reads `store_id` out of a plaintext JSON header and then queries with the **service-role key**, which bypasses RLS entirely.

```ts
// src/app/api/transactions/route.ts:26
const authData = request.headers.get('x-auth-data');
if (!authData) return NextResponse.json({ error: "Unauthorized..." }, { status: 401 });
const parsed = JSON.parse(authData);
store_id = parsed.store_id;
```

There is no signature, no cookie, no session, no JWT check. Anyone can read, write, or delete any store's data:

```
curl -H 'x-auth-data: {"store_id":"<any-uuid>"}' https://<host>/api/transactions
```

**Affected:** `api/transactions/route.ts:26` (GET), `:108` (POST — write into any store), `:285` (DELETE), `api/transactions/analytics/route.ts:70`, `api/cash-shifts/route.ts:58`, `api/cash-adjustments/route.ts:49`.

`src/middleware.ts` → `src/lib/supabase/middleware.ts:40-44` confirms nothing is enforced upstream.

**Fix:** issue a signed session token at login and verify it server-side. The primitive already exists and is imported by nothing: `src/lib/auth/jwt.ts` (`jose`, already a dependency).

> **Partially addressed (activity logging change).** The **admin** half of this is now done: `src/lib/auth/adminSession.ts` issues an HS256 session into an httpOnly cookie at `POST /api/admin/login` and verifies it server-side, and `GET /api/admin/activity` is gated on it. It deliberately does **not** reuse `src/lib/auth/jwt.ts` — that file's payload is `restaurantId` (TableMind scaffolding) and it carries the P0-8 fallback secret. `ADMIN_JWT_SECRET` throws when unset rather than falling back.
>
> The **store** half is unchanged. `POST /api/activity` still reads `x-auth-data`, because there is no signed store session to read instead. It is bounded: stores can only write to that endpoint, never read it, so a forged header injects junk into one store's own log and nothing more. When store sessions become signed, that route changes in one place.

### P0-2 🔴 Three API routes have no authentication at all

| Route | Exposure |
|---|---|

### P0-3 🟡→ MOSTLY FIXED 2026-08-28 — Privilege escalation by omitting a field

**Fixed for the absence case; the forgery case remains and is P0-1.**

Both cash routes now resolve the caller through one shared helper,
`src/lib/auth/apiCaller.ts` (`resolveCaller`). A missing `user_id` is a **401**,
not a promotion. The owner is identified **positively** — their session id is
the store id, which the server has just loaded — rather than inferred from an
absent field. Employees are looked up in `store_users`, scoped by `store_id`,
and get the permissions the database says they have.

`src/lib/auth/apiHeaders.ts` is the matching client-side builder and always
sends `user_id` (the owner sends their store id). The sync engine's own header
builder was updated to match, so queued cash writes keep replaying.

**What is still open:** `x-auth-data` remains unsigned, so a caller who knows a
store's UUID can still forge `user_id === store_id` and claim to be the owner.
Escalation now requires knowing and forging a specific UUID rather than deleting
a field — a real reduction, not a closure. **These routes should not be
described as authenticated until P0-1 lands.**

#### Original finding


```ts
// src/app/api/cash-adjustments/route.ts:28-30
// No user_id → owner login
if (!userId) {
  return { isOwner: true, userId: null, name: store.username };
}
```

Identical at `api/cash-shifts/route.ts:29-31`. The routes then gate on `caller.isOwner` (`cash-adjustments:77`, `cash-shifts:169,229`). **Any employee who omits `user_id` from the header becomes the owner** and gains full cash-drawer in/out authority.

The comment at the top of `cash-shifts/route.ts` claims "We verify server-side (not from client claims) because this feature guards money." The code does the opposite.

### P0-4 🔴 Passwords are plaintext, compared in the browser, and logged

```ts
// src/app/api/admin/login/route.ts:28,39-44  ← REMOVED, see below
console.log("Login attempt:", { username, password, fetchError, admin });
const isValidPassword = admin.password_hash === password;
console.log("Password comparison:", { storedHash: admin.password_hash, inputPassword: password, isValid: isValidPassword });
```

Both the submitted password and the stored value are written to server logs. The column is named `password_hash` but holds plaintext.

> ✅ **The credential logging in `api/admin/login/route.ts` is fixed** (activity-logging change). Both `console.log` calls are gone; failures are now reported without either value. **The rest of P0-4 is untouched**: the comparison is still plaintext `===`, store-owner login still happens client-side with `password_hash` fetched down to the browser, `bcryptjs` is still unused, and `offlineAuth.ts` still caches the plaintext password with no expiry.

Store-owner login is worse — it happens **client-side**, and the browser fetches the stored credential down to itself:

```ts
// src/app/(auth)/login/page.tsx:90,107
.select("id, username, password_hash, license_expires_at")
if (store.password_hash !== password) { ... }
```

An attacker can retrieve `password_hash` for any username with the public anon key, regardless of the comparison.

And `src/lib/auth/offlineAuth.ts:44-51` caches the **plaintext password** in localStorage for offline login. `cachedAt` is recorded but never checked, so cached credentials never expire; `license_expires_at` is cached but not enforced offline, so offline login bypasses license expiry.

`bcryptjs` is already a dependency and is imported nowhere.

### P0-5 🔴 RLS provides no protection

```sql
-- supabase/migrations/002_admin_rls.sql:7-10
CREATE POLICY "admin_users_select" ON admin_users FOR SELECT USING (true);
CREATE POLICY "admin_users_all"    ON admin_users FOR ALL    USING (true);
```

With the public `NEXT_PUBLIC_SUPABASE_ANON_KEY`, anyone can `SELECT * FROM admin_users` and read every admin's plaintext password, or `INSERT` a new admin. `supabase/seed.sql:11` seeds `admin` / `admin123`.

Same `USING (true)` on all four verbs for `store_users` (which holds `password_hash`), `cash_shifts`, and `cash_adjustments` — `010_store_users.sql:23-26`, `021_cash_management.sql:60-68`.

The "real" policies are simultaneously useless in the other direction: `001_initial_schema.sql:95-98` gates `stores`, `products`, `transactions`, `transaction_items` on `store_id = auth.uid()`. The app never uses Supabase Auth, so `auth.uid()` is always `NULL` and every one of those policies evaluates false. Yet the login page reads `stores` and the sync engine reads `products` with the anon key — meaning **RLS has been disabled or overridden directly in the production database, and the migrations in this repo do not describe the deployed state.** `024_fix_stock_decrement_security.sql:4-8` documents exactly this discovery for the RPC.

`decrement_stock` is `SECURITY DEFINER` with **no `SET search_path`** (`024:39`) — a standard privilege-escalation hazard — and is `GRANT`ed to `anon` (`024:42`). Its `p_store_id DEFAULT NULL` legacy branch (`024:31-37`) lets any anonymous caller decrement stock on any product in any store.

**Before fixing:** dump the *actual* production RLS state. The repo is not a reliable description of it.

## P1 — Money and data correctness

### P1-1 ✅ FIXED 2026-08-24 — Offline sales are recorded with the wrong date

**Fixed.** `src/lib/sync/engine.ts` now sends `created_at` from the queued row in
the sync payload, and `POST /api/transactions` accepts it — clamped to `<= now()`,
so a till with a fast clock cannot write sales into a shift that has not started
yet. An absent or unparseable value falls through to the column default, which is
the correct behaviour for an online sale (it is happening now) and preserves the
old behaviour for anything else.

No schema change was needed; the column already existed and already defaulted.

#### Original finding

`QueuedTransaction` carries `created_at` (`src/lib/db/localDB.ts:68`), but the sync push payload at `src/lib/sync/engine.ts:313-345` never sends it, and `POST /api/transactions` (`:162-186`) never sets it. So `created_at` falls back to the column default `NOW()` — **the moment of sync, not the moment of sale**.

A sale made offline on Friday and synced on Monday is recorded as a Monday sale. This corrupts:
- cash-shift reconciliation, which matches on `created_at::date = v_business_date` (`021_cash_management.sql:106`, `cash-shifts/route.ts:108-109`)
- hourly and day-of-week analytics (`analytics/route.ts:174-190`)
- retention cleanup

**One-line fix, large correctness payoff.** Highest value-per-effort item in this document.

### P1-2 ✅ FIXED 2026-08-28 — USD payments are double-counted in the cash drawer

**Fixed.** All drawer arithmetic now runs through `summariseShift()` in
`src/lib/cashShift.ts`, which computes cash into the drawer as
`SUM(amount_paid) - SUM(change_given)` and **nothing else**. `usd_amount_paid`
is carried for display only and never added back into the LL total, because
those dollars are already inside `amount_paid` at `RETURN_RATE`.

`get_cash_shift_summary()` — the function that did the double-add — was
**dropped** in migration `027`. It had never been called from `src/` (the route
re-implemented the aggregation in TypeScript), so it was a second, wrong
definition of the drawer maths sitting in the database waiting to be trusted.

**A second, larger bug was found in the same place and fixed with it.**
`amount_paid` is **gross tender**, not net takings: `checkout/page.tsx:333-335`
records everything the customer handed over and stores `change_given`
separately. The old cash page summed `amount_paid` alone and set change to
zero, annotated *"change is already netted into amount_paid per transaction"*.
It is not. On a 100,000 LL sale paid with a 200,000 note, the page counted
200,000 into the drawer and expected a figure **100,000 too high** — an error
larger than the USD double-count it sat next to, on every non-exact sale.

#### Original finding


Checkout stores `amount_paid` as the LL-equivalent of *everything*, including the USD portion:

```ts
// src/app/checkout/page.tsx:70
const totalPaid = paidLL + convertUsdToLlForReturn(paidUSD);
```

…and separately stores `usd_amount_paid: paidUSD` (`:190`). `get_cash_shift_summary` then adds both:

```sql
-- supabase/migrations/021_cash_management.sql:119-120
(v_opening_ll  + txn_agg.cash_in     - txn_agg.chg     + ...) AS expected_ll,
(v_opening_usd + txn_agg.cash_in_usd - txn_agg.chg_usd + ...) AS expected_usd
```

`cash_in` (`SUM(amount_paid)`) already contains the USD converted at 89,000; `cash_in_usd` contains the same dollars again. **Expected LL is overstated by the USD take on every mixed-currency sale**, and the same double-count applies to change. `perUser` totals share the basis (`cash-shifts/route.ts:129`).

### P1-3 ✅ FIXED 2026-08-25 — Money columns overflow at ~1,100 USD

**Migration `025_widen_money_columns.sql` was applied to production by the owner
on 2026-08-25, and the fix is empirically confirmed:** a transaction of
**150,000,000 LL** — 1.5× the old `DECIMAL(10,2)` ceiling of 99,999,999.99 —
inserted with `201`. Before the migration this threw `numeric field overflow`,
the client read the 500 as an outage, queued the sale, and it failed on every
retry until dead-lettered.

#### Original finding

`supabase/migrations/025_widen_money_columns.sql` widens `transactions`
(`subtotal`, `total_amount`, `amount_paid`, `change_given`), `transaction_items`
(`unit_price`, `total_price`) and `products` (`cost_price`, `selling_price`) to
`DECIMAL(14,2)`.

**This is still open until the owner applies it.** There is no automated migration
step in the Vercel deploy. The file carries a pre-flight query (the repo is not a
reliable description of production — see P0-5) and a locking warning: `ALTER COLUMN
… TYPE` takes an `ACCESS EXCLUSIVE` lock and may rewrite the table, so it must be
run off-hours, one statement group at a time.

**A second instance of the same mistake was found while sizing it and is included:**
`products.profit_percentage` is `DECIMAL(5,2)` (max 999.99) but is *computed from
LL prices* by the inventory form — `handleSellingPriceChange` →
`calculateProfitPercentage` in `(shell)/pos/products/page.tsx`. Cost 1,000 LL
against selling 185,000 LL yields 18,400, which overflows and fails the product
save with an opaque error. Widened to `DECIMAL(10,2)`.

USD columns are deliberately untouched — they hold dollars, where `DECIMAL(10,2)`
is ~100M and unreachable.

#### Original finding

`transactions.subtotal` / `total_amount` / `amount_paid` and `transaction_items.unit_price` / `total_price` are `DECIMAL(10,2)` (`001_initial_schema.sql:54-57,69-70`) — maximum **99,999,999.99**. Amounts are denominated in **LL**, where one item is routinely ~185,000.

A basket over roughly 1,100 USD throws `numeric field overflow`. The POST handler returns 500, and the client treats that as an offline condition and drops the sale into the offline queue — **where it will fail forever on every retry**.

`cash_shifts` was correctly widened to `DECIMAL(12,2)`. `transactions` never was. `products.selling_price` has the same ceiling.

### P1-4 ✅ FIXED 2026-08-31 (migration 038) — Sale + line items + stock decrement was not atomic

`src/app/api/transactions/route.ts:229-267` makes three separate round-trips — insert transaction, insert items, loop N× `rpc("decrement_stock")` — with no transaction wrapper. Both failure modes are explicitly swallowed:

```ts
if (itemsError) {
  console.error("Transaction items error:", itemsError);
  // Transaction created but items failed - still return success but log error
}
...
if (stockError) {
  console.error(`[API] Stock decrement failed for product ...`);
  // Don't fail the transaction — log and continue.
}
```

A partial failure produces a header-only sale with no line items (invisible on the receipt, breaks analytics) or un-decremented inventory — and the client is told `201 Created`.

Compounding: the items insert (`:230-239`) **does not persist `unit_price_usd` / `total_price_usd`** even though the client sends them (`engine.ts:342-343`, `checkout/page.tsx:199-200`). `transaction_items` has no such columns. Silent field drop.

**Fix:** one `create_transaction(...)` plpgsql function.

---

**FIXED** by `create_sale` in migration **038**. All three writes — the
transaction, its line items and the stock decrements — now happen inside one
plpgsql function and therefore one database transaction. All of it lands or
none of it does.

Previously the transaction row committed first, and a failure on the items
insert was deliberately swallowed (the sale already existed, so failing the
request would have been worse) — leaving a sale with no lines: an empty
receipt, no kitchen ticket, and analytics silently under-counting.

The multi-step path remains as a fallback for a database without 038, so the
deploy is safe in either order.

**Measured side effect:** the money path went from THREE serial round trips to
one. `POST /api/transactions` for a 3-line sale, median of 15:
**1226ms → 307ms** (p90 1243ms → 409ms).

### P1-11 ✅ FIXED 2026-08-31 (migration 038) — A queued sale from a DELETED employee was rejected and dead-lettered

**Found 2026-08-31 by the Phase 1.3 contract suite** (`harness/contract/sale.test.ts`),
on its first run against the fixture store.

`POST /api/transactions` returns **500** when `user_id` names a `store_users`
row that no longer exists. The database raises `23503` on
`transactions_user_id_fkey`.

**Why this takes money.** The failure needs three ordinary things to line up:

1. A cashier rings sales offline. They queue in `offline_queue` carrying that
   cashier's `user_id`.
2. The employee leaves and an admin removes them. `DELETE
   /api/admin/store-users` is a **hard delete**, not a deactivation.
3. The till reconnects. Sync pushes the queued sales, the insert violates the
   foreign key, and the route returns 500.

The client reads **any** 500 as an offline condition, so it retries, exhausts
its five attempts, and **dead-letters** the sale. The money was taken at the
till and the sale never reaches the server.

`ON DELETE SET NULL` (migration 015) makes sales *already recorded* survive the
employee's deletion. It does nothing for sales still sitting in a device's
queue, which is the case that matters.

**Contradicts invariant #10** in `docs/PERF-REFACTOR-PLAN.md`: a sale is never
blocked by a failed lookup. Shift resolution already degrades correctly here —
an unresolvable shift yields a null `shift_id` and the Unassigned bucket, and
the sale stands. The user reference does not degrade the same way.

**FIXED** by `create_sale` in migration **038**: an unresolvable `user_id` is
coerced to `NULL` at insert, exactly as shift resolution already degrades to a
NULL `shift_id`. The sale is **recorded** rather than lost, and `user_name` —
stored denormalised alongside — still says who rang it. The coercion is scoped
by store, so a forged id from another tenant is also dropped rather than
recorded.

**Verified:** `harness/contract/sale.test.ts` now pins the FIX — a sale from a
deleted employee returns 201, the row exists, `user_id` is NULL, `user_name`
survives, and the total is right. If it ever returns to 500, a shop is losing
sales again.

**Not yet known:** whether any live store has dead-lettered a sale this way.
Worth a query against `offline_queue` dead letters before the fix ships.

### P1-12 🟡 A menu item scanned before recipes load is sold as a plain line

**Found 2026-08-31 by the Phase 1.4 E2E suite** (`harness/e2e/menu.spec.ts`).

The till reads recipes from `store_recipes_<store_id>` in **localStorage**.
That key is empty on a cold device; `refreshRecipes()` fills it in the
background *after* first paint. A menu item scanned inside that window has no
known recipe, so `handleTileAdd` treats it as an ordinary product:

- **no modifier sheet** — the cashier cannot say "no pickles"
- **`modifiers` is NULL**, so the kitchen board never shows the ticket. It
  filters on `modifiers IS NOT NULL`, and NULL means "not a food order".
- **stock decrements the MENU ITEM's own meaningless `stock_quantity`** rather
  than its ingredients, so the ingredient counts silently drift

Nothing errors. The sale completes and looks normal.

**How wide is the window?** Small on a warm till, and it closes permanently
once the cache is populated. But it is widest exactly when a device is new, has
just had its storage cleared, or has been evicted under quota pressure — and
`refreshRecipes()` needs the network, so on a shop's slow connection it is
wider still. A device that is offline on first launch has **no** recipes at
all, and every menu item it sells that day takes this path.

**Root cause is a conflation:** an absent cache and an absent recipe are
represented the same way. "Recipes not yet loaded" and "this product has no
recipe" are different facts and need to be distinguishable.

**Fix:** belongs in **Phase 3**, when the client data layer is rebuilt — the
new primitive should expose a loading state, so the till can hold a scanned
menu item rather than silently degrade it. A cheaper interim option is to gate
the plain-add path on recipes having loaded at least once.

**Recorded, not fixed:** Phase 1 freezes behaviour. `menu.spec.ts` pins the
degraded behaviour in a test that skips itself once the cache is warm.

### P1-5 🔴 Stock can go negative; no input validation on any route

There is no stock check anywhere — not in `cartStore.addItem` (`:18-80`), not in `incrementQuantity` (`:111`), not in the API. `001_initial_schema.sql:117` is explicit: `-- Allows stock to go negative — no guard clause`. Two cashiers on two devices will both sell the last unit.

More broadly, **no route validates input**. There is no Zod/Valibot in the project. `POST /api/transactions` writes `body.subtotal`, `body.total_amount`, `body.amount_paid`, `item.quantity`, `item.unit_price` straight to the database with no type, range, or sign checks. A `quantity` of `-1000` is accepted and **increments** stock via `decrement_stock`. `/api/products/import` validates only `Array.isArray(products)` (`:132`) — `ProductImportData` is compile-time only.

### P1-8 ✅ FIXED 2026-08-16 — Barcode lookup ignores store scope

### P2-9 ⚠️ PARTIALLY FIXED 2026-08-16 — Sync engine rough edges

**Fixed in this pass:**

- **`pullProducts` reconcile was destroying the cache.** Worse than the "expensive" note below: the reconcile ID fetch (`engine.ts:251-254`) had no `.range()`, so PostgREST truncated it at 1000 rows and `reconcileProductsCache` deleted every product past that point. The completeness check then re-pulled the whole catalog, and the next sync deleted them again — **a permanent delete/refetch loop every 30s on any store with >1000 products** (live at the current 2,500). Now uses a paginated `fetchAllProductIds()` and refuses to delete unless the fetched ID count matches the server's exact count. The full ID sweep is also skipped entirely unless the cache is *ahead* of the server. Guard logic extracted as the pure function `evaluateReconcile()` in `src/lib/sync/engine.ts` so it can be reasoned about (and re-tested) in isolation.
- **Retry caps now applied uniformly.** Queued transactions had no cap at all; cash and favourite writes incremented `retry_count` without ever checking it. All three are capped now. Transactions are **dead-lettered, never dropped** — a completed sale whose money was taken must not be silently discarded (`getDeadLetterTransactions()`).
- **`getPendingWrites()` inside the push loop** is hoisted out — it was a full table scan per queued transaction.
- **`visibilitychange` was registered on `window`**, where it does not fire on iOS Safari/WKWebView — the primary POS platform. Moved to `document`.

**Fixed 2026-08-19:**

- **The delta branch was never paginated.** The reconcile ID fetch was fixed on 2026-08-16, but the incremental product select immediately above it kept a bare `.gte("updated_at", …)` with a comment asserting that "no pagination [is] needed for small deltas". A bulk price change across a 2,300-product catalogue is not a small delta: PostgREST returned the first 1000 rows and reported success, leaving the rest of the store priced from stale cache until something else forced a full pull. The `BulkPriceDialog` feature made this reachable in one tap. Now paginated, ordered `updated_at, id` (`updated_at` alone is not unique — a bulk write stamps every row with the same `NOW()`).
- **The watermark had no clock-skew margin.** It is a client-side `Date.now()` compared against a server-side `updated_at`. A device running even slightly fast asked for changes since a moment that had not happened on the server yet, permanently skipping everything written in the gap. The query now rewinds 5 minutes; re-fetching a handful of already-current rows is free and idempotent, missing a price change is not.
- **Two copies of the same algorithm could run at once.** `SyncEngine.pullProducts` and the inventory page's own fetch were near-identical implementations that had drifted on the details that matter, and nothing stopped them racing — entering Inventory fires the engine's `visibilitychange` sync too, so both ran a full pull simultaneously. Both now call `refreshProductsIntoCache()` in `src/lib/products/refresh.ts`, which holds a per-store in-flight promise so the second caller joins the first. `evaluateReconcile()` moved there with it and is re-exported from `engine.ts`.
- **`pullProducts` is no longer expensive per sync** (see the "expensive" note below): the full `select("id")` sweep was already skipped unless the cache is ahead of the server, and the delta select now asks for named columns instead of `select("*")`.

**Still open:** cross-tab concurrency (`syncInProgress` is per-instance), the unrecoverable partial insert (P1-4), the over-broad legacy cleanup matching on `product_id` alone, and exponential backoff (retries are still a flat 30s).

#### Original finding

The core is sound — serial push, `syncInProgress` guard, `UNIQUE (store_id, transaction_number)` with a `23505` fallback, cache reconciliation, retry cap. These issues sit around it:

- **Cross-tab concurrency.** `syncInProgress` is per-instance. Two tabs share one IndexedDB but have separate `syncEngine` singletons; both will read `offline_queue` and both will POST. The unique constraint prevents duplicate transactions, but the second tab hits the duplicate branch (`route.ts:125-157`) which **skips** the stock decrement. Correct by luck, not design.
- **Unrecoverable partial insert.** If the transaction insert succeeds but the items insert fails, the retry hits the duplicate branch and the items are **never written**. See P1-4.
- **Retry caps not applied uniformly.** `processPendingWrites` caps at `MAX_PENDING_WRITE_RETRIES = 5` (`engine.ts:26,490-496`), but `processPendingFavoriteWrites` (`frequentlyUsed.ts:244-289`) increments `retry_count` and **never checks it** — a permanently failing favourite write retries forever every 30s. ### P2-15 ✅ FIXED 2026-08-19 — Inventory reloaded itself, and cost 4s to open

Two separate faults, reported together as "the inventory page randomly reloads and takes a while".

**The reload.** `PWAUpdateListener` is the only automatic `window.location.reload()` in the app. It fires on the service-worker `controllerchange` event and was guarded by exactly one condition: the cart is empty. On every screen except the POS the cart is *always* empty, so the guard protected nothing — a cashier part-way through building a bulk selection on Inventory had the page reloaded under them and the selection thrown away. Foregrounding the PWA calls `registration.update()`, and with `skipWaiting` + `clientsClaim` in the generated worker a newly deployed version activates seconds later, which is why it read as "a few seconds after I entered the page". Production only, so `next dev` could never reproduce it.

Fixed by replacing "is the cart empty" with "is anybody mid-task": `src/lib/pwa/reloadGuard.ts` is a hold registry, screens declare their own busy state via `useReloadGuard(active, reason)`, and the update listener defers until every hold clears — retrying on hold release, on the cart emptying, and on the next foreground. The update still applies automatically and silently; it just waits for a safe moment. Holds are registered by Inventory (selection mode, any open dialog, an in-flight submit), Checkout (unconditional), the cash register (any counted-cash dialog) and the POS completion dialogs.

**The 4 seconds.** The page called `fetchProducts(storeId, true)`, and `forceRefresh: true` made `fetchProductsCacheFirst` skip the entire IndexedDB block *including the `onCacheHit` instant-paint callback*. So every entry blocked on three sequential `select("*")` round-trips of 1000 rows, a 2,276-row `bulkPut`, and a full reconcile sweep before rendering anything. The cache is a complete mirror of the catalogue and the POS page already proved the pattern.

Inventory now paints from `getCachedProductsSortedByName()` immediately (name-ordered via the existing `[store_id+name]` index, so the list cannot reshuffle when fresh rows land) and refreshes behind it via `refreshProductsIntoCache()` — still hitting Supabase on every entry, but asking only for rows whose `updated_at` moved. `forceRefresh` is gone as a concept; `fetchProductsCacheFirst` had no other callers and was removed.

- **Offline rendered an empty page.** `fetchProducts` opened with a `connectivity.isOnline` check that toasted "No internet connection" and returned *before* touching the cache — on an offline-first POS holding a complete local catalogue. The cache is now painted first and the toast only fires when there is genuinely nothing to show.

### P2-16 ✅ FIXED 2026-08-28 — A sold product could never be deleted, and the workaround destroyed sales history

Reported as "we can't delete products in inventory because they're linked to transactions".

**The block.** `transaction_items.product_id` was declared in `001_initial_schema.sql:66` as a bare `REFERENCES products(id)` — no `ON DELETE` clause, which in Postgres means `NO ACTION`: the delete is *refused* with SQLSTATE `23503` the moment the product has ever been sold. Since a product worth deleting is almost by definition one that has been sold, the Inventory delete button only ever worked on products nobody had bought. `handleDeleteProduct` caught the `23503` and told the cashier to "consider deactivating it instead" — there is no deactivate feature.

**The workaround was the worse bug.** `api/products/import/route.ts` (`:185-210`) got around the same FK by deleting **every `transaction_items` row and every `transactions` row for the store** before deleting the products, on `mode: 'replace_all'`. Importing a spreadsheet wiped the store's entire sales history. The import dialog's own copy only ever warned that *products* would be replaced, so this was invisible to whoever clicked it — and combined with P0-2 (that route has no auth) it was remotely triggerable.

**Fix:** migration `028_product_delete_preserves_history.sql` replaces the FK with `ON DELETE SET NULL`.

- `product_id` was already a **nullable** FK, and `NULL` was already a live, supported state — a one-off line (an unknown barcode priced at the till) has always been written with `product_id = NULL` (`src/lib/pos/lineItems.ts`).
- The receipt loses nothing: `transaction_items` carries its own denormalised `product_name`, `quantity`, `unit_price`, `total_price`, `currency`. Those are the values *as sold*; they are not read back from `products`. Nulling the FK severs the link to the catalogue row, not the record of the sale.
- **Not `CASCADE`** — that would delete the line items and silently change the totals of completed, already-paid sales.
- The constraint is dropped by lookup in `pg_constraint` rather than by name, because production has diverged from these files before and the default name is not guaranteed.
- `idx_transaction_items_product` added: without it each product delete sequentially scans the whole sales history to null the referencing rows.

The `transaction_items` / `transactions` deletes are removed from the import route; `replace_all` now touches the catalogue only, matching what its dialog always claimed. The Inventory confirm dialog now states that past sales keep the product as it was sold, and the `23503` branch is kept only as a "migration 028 is not applied here" signal.

**Every consumer already tolerated a null `product_id`** — verified before the change, not after: the transactions page's local profit calc filters on `!!i.product_id && byId.has(...)` (`transactions/page.tsx:451`), the analytics route falls back to `item.unit_price` on a cost-map miss and groups its product stats by the denormalised `product_name`, the public receipt route reads only denormalised fields, and `database.ts` / `localDB.ts` both already type the column as `string | null`.

### P2-17 ✅ FIXED 2026-08-30 — The installed iOS PWA opened slowly, showed "Offline" for ten seconds, and turned the whole tab bar into spinners

Reported from a real iPhone: the PWA takes a long time to open, the till says
**Offline** for about ten seconds once it is up, and tapping the nav bar makes
**every** icon start spinning. All three reproduce on desktop and Android in
principle — iOS just loses every race, because an installed iOS PWA is killed
aggressively and therefore cold-launches a brand-new WebView on a brand-new
connection *every single time it is opened*. Desktop and Android reuse a warm
process and a warm connection, so the same defects stay under the threshold
where anyone notices.

**1. The ten seconds was arithmetic, not a coincidence.** `connectivity.probe()`
aborted at `HEARTBEAT_TIMEOUT_MS` (5s) and a failed probe was only ever retried
by the 15s heartbeat. So one slow probe painted "Offline" from t=5s to t=15s —
ten seconds, every time, for a network that was never actually down. The boot
probe is the one most likely to lose, because it fires at module-eval time
against a cold connection while competing with the entire first-load burst.

Fixed by re-probing on a short backoff after a failure (`RETRY_DELAYS_MS`,
1s/2s/4s, then the heartbeat takes over). A genuine outage costs nothing extra —
`fetch` with no network rejects in milliseconds without leaving the device, and
the backoff stops after three attempts, so a three-day outage adds three probes
in total, not thousands. This does **not** weaken offline detection: the first
failure still flips the status to offline immediately, exactly as before. It
only shortens how long a *wrong* offline verdict survives.

**2. The slow launch was self-inflicted congestion.** `/pos` fired roughly
sixteen requests in one tick on mount. Eight of them — three `router.prefetch()`
calls and `warmAppShell()`'s five full HTML documents, fetched
`cache: "no-cache"` so each is a forced round trip — exist purely for a *future*
offline cold start. Nothing on the screen reads any of them, yet they were
racing the requests this launch genuinely needed, the connectivity heartbeat
included. That is what made the probe above lose.

They are now deferred to `scheduleWhenIdle()` (`src/lib/pwa/whenIdle.ts`) and
`warmAppShell()` fetches its routes **sequentially** rather than with
`Promise.all`, so it can no longer fill the connection pool. The idle callback
carries a 4s timeout on purpose: a shell that is never warmed is a till that
cannot cold-open in an outage, so this work must still be guaranteed to run —
just not first.

**3. `networkTimeoutSeconds` 3 → 2 on the `app-shell` rule.** It was written as
pure offline insurance, but it is also a tax paid on every healthy launch: a
cold iOS WebView waits it out with a perfectly good shell sitting in the cache.
Lowering it costs no freshness — Workbox races the timeout against the network
but does not abandon the request, so the fresh document still lands in the cache
for the next launch. `scripts/verify-sw.mjs` confirms the value in the generated
worker.

**4. "All icons start loading" was literal.** `BottomTabBar` and `DesktopNav`
each hold a single `useTransition()` and rendered the spinner on
`isPending && !active`. One flag cannot say *which* tab was tapped, so every
inactive tab spun at once and the bar dissolved — which reads as the app
hanging, not as one destination loading. Both now remember the tapped `href` and
spin only that tab. No effect is needed to clear it: `isPending` goes false when
the transition settles, and the next tap overwrites the href. **Desktop had this
too** and nobody had reported it.

**Verified:** `npm run typecheck` clean (after `rm -rf .next` — stale route
types), `npm run lint` reports nothing new in the six touched files, and
`npm run build` regenerated `public/sw.js` with all five `verify-sw` assertions
passing and `networkTimeoutSeconds:2` present on the `app-shell` rule. No money,
auth, or sync path was touched; the offline queue, rounding rules and store
scoping are untouched. Still wants a real-device pass on an iPhone, per the
no-suite rule.

Requested as "performance, speed, connectivity matter most — find whatever is
causing bottlenecks and fix them". Most of what follows was already scanned and
prioritised in **Deferred — scanned, prioritised, not built** above; this is
that list being built, plus what a fresh pass found.

#### Server — the checkout path

**A `COUNT(*)` over the store's whole sales table ran on every sale.**
`012_auto_cleanup_trigger.sql` installed an `AFTER INSERT … FOR EACH ROW`
trigger on `transactions` that, per row, read the store's retention settings,
counted every transaction the store has ever made, conditionally deleted the
oldest, and then ran a second unconditional `DELETE` for the time cutoff whether
or not anything qualified. All inside the transaction that takes the customer's
money, and once per row on a batched insert. At the 5,000-transaction default
that is a 5,000-row count plus two delete scans, per sale.

Migration **037** drops the trigger and its function. The policy is unchanged —
`scheduled_transaction_cleanup()` (013) has always implemented it, and
`cleanup_old_transactions_for_store()` does one store. It now runs from
`POST /api/transactions` at most once an hour per server instance, inside
`after()` so it happens once the response has already gone back to the till —
the same opportunistic pattern `POST /api/activity` uses for partition
maintenance. 037 also registers a daily pg_cron job **if** the extension happens
to be enabled, guarded so it cannot fail the migration when it is not.

**N+1 stock decrements became one call.** The route awaited a separate
`decrement_stock` RPC per line. A ten-line sale was ten serial round trips from
the Vercel function to Postgres — and a made-to-order sale is worse, because a
sandwich decrements every ingredient in its recipe rather than itself.
`decrement_stock_batch(p_store_id, p_items)` (037) does the lot in one
statement, summing repeated product ids first. Semantics are deliberately
identical: store-scoped, negative stock allowed, unknown ids skipped. It takes
**no** NULL-means-skip tenancy default — that branch of `decrement_stock` is
audit P0-5 and is not reproduced. `decrement_stock` itself gained the
`SET search_path = public` it was missing, body untouched.

**A duplicate pre-check ran on 100% of sales.** A `select id where
transaction_number = …` before every insert, to catch the sync engine pushing
the same queued sale twice. The `UNIQUE (store_id, transaction_number)`
constraint (016) plus the existing `23505` branch already answer that, and the
branch returns the identical `{ transaction, duplicated: true }` response.
Removed: one round trip per sale in every shop, to pre-empt something the
database rejects for free.

**The line-item insert and the decrements now overlap.** They read nothing of
each other's, so they go out as one wave instead of two.

Net, a ten-line sale: **~14 serial round trips → 3**, with the trigger's table
scan gone from inside the write.

**Four duplicate indexes on `transactions` dropped.** Every index is written on
every INSERT, so a duplicate is a pure tax on checkout. Migrations 003, 014 and
019 had each independently created `(store_id, created_at DESC)` — three
identical copies — and 001's `(store_id)` and `(created_at)` are strict prefixes
/ direction-duplicates of survivors. `idx_transactions_store_created_at` and
`idx_transactions_created_at_desc` are kept and cover every query that used the
dropped ones.

**The middleware built a Supabase client per request and never used it.**
`updateSession` constructed a full `createServerClient` — GoTrue, PostgREST,
Realtime, Storage, cookie adapter — then returned, with its own comment saying
no session check was needed. The matcher covers every navigation and every
`/api/*` call, so the connectivity heartbeat paid for it every 15 seconds per
tab, in front of the one endpoint whose entire job is to answer fast. It is a
passthrough now. **No authorization was removed** — there was none (P0-1); the
docblock says where the signed-session check belongs when it exists.

#### Server — the report that was silently wrong

`GET /api/transactions/analytics` selected every transaction in the window WITH
every nested line item and aggregated in JavaScript, with no `.limit()`.
Measured at 700-2,900 ms on a store with **forty** sales, to return 3 KB. The
worse half: **PostgREST silently caps an unbounded select at 1,000 rows**, so
any store past 1,000 sales in the window was shown revenue and profit computed
from an arbitrary 1,000 of them, with nothing on screen to say the figure was
partial. Its `.in("id", …)` product lookup also built a URL out of every product
id in the range, which 414s.

`get_transaction_analytics()` (037) aggregates in Postgres — the same rule that
produced `get_shift_totals` and `get_unassigned_totals` (§11a). Hour and weekday
buckets use `AT TIME ZONE`, so Beirut's DST changes resolve per instant exactly
as the `Intl` path did.

**The exchange rate stays in `format.ts`.** The function returns `cost_ll` plus
`usd_cost_lines` — raw `(cost_price, quantity)` pairs — and the route applies
`productCostInLL()` per product, which is what it did before. Summing the USD
side in SQL would round once instead of per product and quietly move the figure.
The "unknown product ⇒ cost = unit_price" fallback is reproduced verbatim.

The JS path is kept as a fallback for a database without 037, with both defects
fixed: it pages through the window instead of accepting the 1,000-row cap, and
chunks the product lookup at 200 ids. Same fallback shape as
`decrement_stock_batch`, so **037 and this code can be deployed in either
order.**

#### Client — the cold-launch burst

`/pos` fired ~16 requests in one tick on mount. Eight existed only for a FUTURE
offline launch (three `router.prefetch`, five `warmAppShell` documents fetched
`cache: "no-cache"`), and were deferred to idle in the previous change; the
remainder is real work.

**Six passes over the catalogue became one.** An effect built the barcode and id
maps, then four memos built the sellable list, ingredient names, ingredient
prices and ingredient products — six walks and six allocations over `products`,
on first paint and again after every background sync, i.e. while the cashier is
scanning. On a 3,000-item store that is ~18,000 iterations a time. Worse, the
maps were **state set from an effect**, so every catalogue change rendered the
whole till twice: once with the stale index, then again after the effect.
`productIndex` is one memo producing all of it, correct in the render that
produced it.

`savedProducts` also did `sellableProducts.find()` per starred product — a full
catalogue scan each, ~60,000 comparisons for 20 favourites. Map lookup now.

**Inventory read localStorage once per row per frame.** Each row called
`isFrequentlyUsed()`, which is a synchronous `getItem` + `JSON.parse` +
`Array.includes`. The list is virtualised to ~16 rows and the virtualiser
re-renders on every scroll frame, so scrolling meant ~16 storage reads and 16
JSON parses per frame on the main thread — the "165 reads for 9 keystrokes"
finding above. One memoised `Set` per render pass now, keyed on the same
`freqVersion` that already invalidated it.

**`--app-h` was rewritten on every scroll frame.** `ViewportHeightSync` wrote the
custom property unconditionally on every `visualViewport` scroll — which fires
per frame while Android's URL bar retracts — invalidating style for the whole
document each time, usually to the same value. Writes are now skipped when the
number is unchanged, and measurement is coalesced to one `requestAnimationFrame`
so `resize` and `scroll` in the same frame cannot force two layout flushes.

**The Supabase browser client read localStorage on every request.** Its
`global.fetch` wrapper existed to parse `tablemind_auth` and set an
`x-restaurant-id` header — dead TableMind scaffolding: the tenancy column is
`store_id`, nothing reads the header, no RLS policy references it, and the key
it read has never been written by this app. Removed, along with the unused
`createClientWithAuth` twin. The "ALWAYS create a fresh client - no caching!"
comment was also simply **false** — `createBrowserClient` has always returned a
cached singleton in the browser unless `isSingleton` is set explicitly.

**The offline-queue counters stopped deserialising the queue.** `getQueuedCount`
/ `getDueQueuedCount` / `getDeadLetterCount` each did
`orderBy("created_at").toArray()` and took `.length`, allocating every queued
sale with its whole `items` payload to read a number off it. `getDueQueuedCount`
runs on a 30-second interval for as long as the app is open. `.filter().count()`
now — the scan is unavoidable (`failed_permanently` is a boolean and IndexedDB
cannot index booleans) but the allocation is not.

**Foreground syncs are throttled.** `visibilitychange` ran a full sync — a
catalogue delta pull, a queue flush and a pending-writes pass — on *every*
foreground, and double-fired, because connectivity also re-probes on
visibilitychange and a probe resolving to "online" triggers `syncNow()` through
the subscriber. `syncInProgress` and the cross-tab lock made that harmless but
not free. 20 s minimum gap, comfortably under the 30 s retry interval.

#### Client — Android frame rate and payload

**The backdrop blur is off on weak devices, and cheaper everywhere.** `.glass`
runs `backdrop-filter: blur(20px) saturate(150%)` on four elements floating over
the **live camera feed** — globals.css itself calls it the single most expensive
thing this UI asks of a GPU. Its kill-switch was `.legacy`, which only fires on
browsers that cannot parse `oklch()` (Chrome ≤110, i.e. Windows 7 tills), so
every cheap modern Android paid it in full. `BrowserGate` now also sets
`.low-power` from `deviceMemory <= 4 || hardwareConcurrency <= 4` — both hints
are Chromium-only, so iOS never matches and keeps the effect, which is right
(WebKit composites it cheaply and iPhones are not the device this is about).
Where it does run, the radius is 12px rather than 20px: blur cost scales with
radius, and behind a 72%-opaque panel the two are not distinguishable — the
background-color is doing the legibility work.

**918 KB (22%) removed from every install and every service-worker update.** The
precache was **4.18 MB**. The single largest item was html2pdf.js →
jsPDF + html2canvas + canvg + their bundled core-js, at 918 KB across two
chunks, serving exactly one Download button on `/receipt/[id]` — the public page
a **customer** opens from a receipt QR. The till never loads it, and it cannot
work offline anyway because the page fetches the receipt from the API. It was
already behind a dynamic import; it was the *precache* that shipped it to every
shop on every deploy.

Excluding it needed both halves: a `splitChunks` group in `nextConfig.webpack`
giving it the stable name `pdf-export` (content-hashed names cannot be matched
by a pattern), and a `/pdf-export/` entry in `workboxOptions.exclude`. It is
still served and runtime-cached by the default `next-static-js-assets` rule when
someone actually presses Download. **Precache: 4.18 MB → 3.28 MB.**

> `workboxOptions.exclude` has the **same footgun as `runtimeCaching`**:
> supplying it REPLACES next-pwa's three defaults (non-preloaded `.woff2`,
> `.map`, `manifest-*.js`). The array re-lists all three. Dropping them puts
> megabytes of source maps into every install, silently, in a generated file
> nobody reviews.

`scripts/verify-sw.mjs` gained two checks for exactly that — "the precache
manifest excludes source maps" and "the PDF exporter is NOT precached" — so both
halves are asserted at build time. Seven checks now.

#### Scanned and deliberately NOT changed

- **`React.memo(ProductRow)` is still defeated by six inline closures.** The
  correct fix is stable callbacks; a custom comparator is not safe here, because
  those closures capture parent state (`toggleFavourite` reads the favourites
  set, `toggleSelect` reads the selection) and skipping re-renders would leave
  rows holding stale ones. The expensive half — a localStorage read per row per
  frame — is fixed above, and the measurement in the production pass was 77 ms
  to paint 2,278 products with zero long tasks. Worth doing properly, not worth
  doing riskily.
- **The History list is not virtualised.** Default filter is "today", so it is
  normally a shift's worth of rows; it only grows via "Load older". The
  inventory page's grouped-virtualiser pattern ports here, but it is a rendering
  refactor of a money screen and did not belong in the same change as the
  money-path work.
- **Two barcode libraries are both precached** — ZXing (411 KB, Android and
  desktop) and Quagga2 (149 KB, iOS). A given device needs one, but the
  precache is platform-blind and camera scanning must work offline on both.
- **`polyfills-*.js` (110 KB)** is Next-managed and `nomodule`-gated.

### P2-20 🟠 CSV `replace_all` is broken for any store that has recipes

**Found 2026-08-31 by the Phase 1.4/1.7 contract suite**
(`harness/contract/csv-import.test.ts`).

`POST /api/products/import` with `mode: 'replace_all'` returns **500** —
*"Failed to clear existing products"* — for any store with recipe rows.

The bulk delete

```
supabase.from('products').delete().eq('store_id', storeId)
```

collides with `recipe_components_ingredient_product_id_fkey`, which is
`ON DELETE RESTRICT` (migration 031). That constraint is **correct and
deliberate**: deleting an in-use ingredient should be refused rather than
silently breaking a recipe, the same principle as `cash_shifts.register_id`.
The two features were simply never tried together.

**Who this hits:** bakeries, coffee shops and snack counters — precisely the
store types §13 of `CLAUDE.md` exists to serve. For them the feature does not
work at all.

**It fails safe.** The delete is a single statement, so nothing is removed and
the catalogue is left exactly as it was. That is why this is P2 and not P1: no
data is lost. What is lost is the feature, plus an owner's afternoon, because
the error names neither the cause nor a way forward.

**Fix options, cheapest first:**

1. **Tell the truth in the error.** Detect `23503` and say which products are
   in use by recipes. Smallest change; turns a dead end into an instruction.
2. **Delete recipes for products being replaced**, inside the same transaction.
   Needs a decision: silently discarding an owner's recipes during a
   spreadsheet import is arguably worse than refusing.
3. **Exclude ingredients from `replace_all`**, so the sellable catalogue is
   replaced and ingredients are left alone. Probably closest to intent — a CSV
   of sellable products is not a statement about the ingredient list.

Not urgent, but it should not be discovered by an owner.

### P2-19 ✅ FIXED 2026-08-30 — Performance sweep, second pass: per-request waste, request depth, and work nobody asked for

Follow-on to **P2-18**. That pass took the obvious weight off the checkout path;
this one goes after the cost paid on *every* request regardless of what it does,
and after requests that should never have been made at all.

#### `/api/health` runs on the Edge now

This is the most-called endpoint in the product by a wide margin — every open
tab probes it every 15 seconds all day, in every shop, plus once on every
launch, every foreground and every `online` event — and it returns a two-field
JSON object while touching nothing.

It was a Node serverless function, measured at **195-204 ms warm** and the RTT
floor for the whole app, with a cold start in front of that. `runtime = "edge"`
removes the cold start and answers from the PoP nearest the shop rather than the
function region. That is the difference between a probe that resolves before the
boot burst is over and one that loses the race and paints "Offline" — the exact
mechanism behind P2-17. Confirmed in `middleware-manifest.json`:
`edge functions: [ '/api/health/route' ]`.

> Nothing in that file may import a Node-only dependency — no Supabase client,
> no service-role key, no `cookies()`. The moment one appears it goes back to
> Node and the heartbeat gets slow again.

#### The service-role client was rebuilt on every request

`createServiceRoleClient()` did `await cookies()` and handed @supabase/ssr a
full cookie adapter, then constructed a `createServerClient` — GoTrue session
storage, realtime, storage, postgrest — **on every request to all nineteen
routes that use it**. None of it did anything: the service-role key bypasses RLS
and never authenticates as a user, and this app has no Supabase Auth at all
(CLAUDE.md §5), so there has never been a session cookie to find.

It is now a plain `@supabase/supabase-js` client with `persistSession`,
`autoRefreshToken` and `detectSessionInUrl` all off, memoised at module scope —
which is what `api/admin/login` and `api/products/export` already did by hand.
On a warm instance "build a client" becomes a property read. The signature stays
`async` so no call site changed.

The dead `createClient(restaurantId?)` export in the same file went with it:
zero importers, and it carried the `x-restaurant-id` TableMind scaffolding.

#### Request depth: auth no longer sits *in front of* the read

`GET /api/transactions` was three round trips deep before reading a single sale:
resolve the caller, then fetch the store's retention settings, then query — on
an endpoint measured at 700-2,700 ms. The first two read nothing of each
other's, so they now go together. Depth 3 → 2.

The same shape applied to `/api/categories`, `/api/recipes` and `/api/combos`,
which the POS fires **all three at once** on launch. Each was
`requireCaller` → query, sequentially. A shared `callerAndRead()` helper in each
route overlaps them.

This is the trade `GET /api/cash-shifts` already documents in its "Wave 1"
comment, and it is safe for the same reason: the read is already scoped to the
`store_id` the caller is claiming, so a failed auth discards a read of the
caller's **own** store and never touches another tenant. Nothing is returned
until the caller is confirmed.

#### `resolveCaller` de-duplicates overlapping lookups

Opening the POS issues three requests at the same instant; the cash page issues
three of its own. Each ran an identical `stores` / `store_users` read in front
of its handler — six identical queries within a few milliseconds.

`resolveCaller` now shares an **in-flight** promise per `store|user`. Entries are
deleted the moment they settle, so a completed answer is never reused and a
permission change or a deactivation takes effect on the very next request.

> A TTL cache would collapse more, including non-overlapping calls, and was
> **deliberately not done**. This is the only server-side identity check the app
> has, and holding a settled answer would delay revoking an employee — a real
> behavioural change on the path that governs cash. Overlap-only dedup buys most
> of the win and changes no observable behaviour at all.

#### The cart was serialised to localStorage twice per scan

`partialize` persisted both `lanes` **and** `items`, and `items` is a mirror of
`lanes[activeLaneId].items` (CLAUDE.md §6a). So every cart mutation ran a
synchronous `JSON.stringify` plus a `localStorage` write over the active lane's
lines *twice* — on the main thread, on the money path, on every scan and every
quantity change. On a thirty-line basket that is the largest single blocking
cost of ringing up an item.

`items` is no longer persisted. Nothing is lost: `onRehydrateStorage` already
re-derives it from the active lane unconditionally, and the two cannot drift
because `commitItems()` is the single writer of both. Carts persisted before
lanes existed still carry `items` in storage and still take the legacy branch
there, which reads it — that path is untouched, and `version` stays 1 because
nothing `migrate()` needs to see has changed.

#### Menu data is no longer fetched by stores without menus

`/pos` and `/pos/products` each fired `refreshCategories` + `refreshRecipes` +
`refreshCombos` unconditionally on mount — three network round trips, each with
its own caller resolution, on every visit. **`product_categories` and
`menu_items` both default to `false`**, so a plain retail store — most of them —
spent three requests of its cold start fetching data it has no screen for. The
rail is already gated on `product_categories` and the modifier sheet on the
recipes being non-empty, so nothing rendered from them either.

They moved into their own effect keyed on the flags, so a device whose flags
arrive from the database a moment after mount still fetches. The local-cache
reads stay unconditional in the load effect — synchronous, free, and they keep
the first frame right for a store that does have the features.

#### Scanned and found already correct

Worth recording so the next pass does not re-derive it:

- **`saleCompletion.ts`** is already optimal — the sale is made durable in
  IndexedDB, the receipt paints immediately, and the server push is fired
  without an await. Nothing to take off that path.
- **`GET /api/cash-shifts`** is already three genuinely-dependent waves with
  Postgres-side aggregation. The 2,455 ms in the production numbers above
  predates that fix.
- **Background timers** are all either guarded or trivial: the connectivity
  heartbeat suspends when hidden, `flushActivity` returns immediately on an
  empty buffer, `drainActivityBuffer` short-circuits when offline or syncing,
  ProPOSLayout's lane tick only starts when a parked lane has items, and
  `useScanFocus`'s sweep only acts when focus is nowhere.
- **`lucide-react`** is already in Next's default `optimizePackageImports`.
- **No browser source maps are emitted**, so nothing is being shipped there.

#### Scanned and deliberately NOT changed

- **`Geist_Mono` with `preload: false`** was tried and **reverted**: measured
  against the built HTML before and after, this app emits *no* font preload
  links at all, so the change did nothing. Reporting it as a win would have been
  wrong.
- **143 KB of fonts stay precached.** next-pwa's default font exclude
  (`/\/_next\/static\/.*(?<!\.p)\.woff2/`) never matches, because it is tested
  against webpack asset names, which have no `/_next/` prefix — so all eleven
  face files are precached, not just the two preloaded ones. Fixing the pattern
  would drop ~114 KB, and was **not** done: the non-latin subsets are exactly
  what a Lebanese shop needs for Arabic product names, and excluding them means
  a visible fallback-font regression during an outage. Wrong trade for 114 KB.

#### Verified

`npm run typecheck` clean. `npm run lint` at **207 problems, down from the 217
baseline** — no new findings in any touched file. `npm run build` green with all
seven `verify-sw` checks passing, and `/api/health` confirmed as an Edge
function in `.next/server/middleware-manifest.json`.

**Still needs a deploy to confirm end to end**, and specifically: `/api/health`
re-timed from a phone on a Lebanese connection (the Edge win is a latency claim,
not a build-time one), and a two-tab check that the cart still rehydrates its
active lane after the `partialize` change.

## Offline-survival pass (2026-08-24)

Scope was deliberately narrow: **keep the app open through a multi-day outage, and
never lose a sale.** Server latency, steady-state CPU waste, Android frame rate and
the analytics rewrite were all scanned and deliberately left for later — see
"Deferred" at the end of this section.

### The app shell expired after 24 hours 🔴 — ✅ FIXED

The worst of the findings, and invisible from source alone. HTML is deliberately
not precached (`next.config.ts`), so a runtime cache is the only cached document.
The default `pages` rule that filled that role carries next-pwa's
`maxAgeSeconds: 86400`, and Workbox's `ExpirationPlugin` treats an entry past its
age as a miss *and* deletes it. **The POS opened fine on day 1 of an outage and
died on the browser's offline page on day 2** — with no `fallbacks.document`
behind it. Verified in the generated `public/sw.js`, not inferred.

Fixed with a dedicated `app-shell` NetworkFirst rule with **no `maxAgeSeconds`**.
Two deliberate choices, both load-bearing:

- **A new cacheName, not `"pages"`.** `extendDefaultRuntimeCaching` appends a
  default only when its cacheName is not already taken, so claiming `"pages"`
  would have *deleted* the default rule. A new name leaves it in place beneath
  ours, so the change can only add coverage.
- **`request.mode === "navigate"`**, keeping the rule narrower than the default.
  Custom rules register FIRST, so a broad pattern would have shadowed the asset
  rules. Confirmed in the built worker: `app-shell` is rule 2 of 19 and all 19
  defaults survive.

Staleness is not a risk: NetworkFirst always prefers the network, so a stale shell
is only ever served when there is no network.

**`scripts/verify-sw.mjs` now asserts all three properties** (rule exists, no
`maxAgeSeconds`, has `networkTimeoutSeconds`) by brace-matching the rule's own
options object out of the minified worker. This is the structural guard — the same
pattern that already protects the `/api/health` and `pages` rules after P0-7
regressed twice.

### Cold start hung on a captive portal 🔴 — ✅ FIXED

The `pages` rule had no `networkTimeoutSeconds` (the `apis` and `cross-origin`
defaults both have 10). On this app's signature failure — wifi associated with no
upstream, where `navigator.onLine` is `true` — the navigation fetch hung until the
browser's own 30-90s timeout before the cache was consulted. `app-shell` sets 3s.

### The route pre-warm had never worked 🔴 — ✅ FIXED

`pos/page.tsx` warmed the document cache with three `fetch(..., { method: "HEAD" })`
calls. Every Workbox route is registered with `"GET"` as its third argument, so a
HEAD request was never intercepted — and a HEAD response has no body to serve a
navigation from anyway. It was a no-op for as long as it existed.

Replaced with `src/lib/pwa/warmAppShell.ts`, which writes real documents into the
same cache via the Cache Storage API. Deliberately not `cache.addAll()` — that is
all-or-nothing, so one route failing would throw away the whole warm.

### Storage was evictable 🔴 — ✅ FIXED

`navigator.storage.persist()` was called nowhere. `offline_queue` holds sales whose
money is already in the drawer, and localDB's own comment says those rows are
"never auto-deleted" — true of our code, not of the browser. iOS/Safari ITP clears
script-writable storage after 7 days without site interaction, taking the queue,
the product cache *and* the cached offline credentials, so nobody could even log in
to find out what was lost. Chrome evicts non-persistent origins under pressure.

`src/lib/pwa/persistentStorage.ts` requests the grant once after login and, when
denied, tells the user once that installing the app is what protects their sales.

### A full disk silently lost sales 🔴 — ✅ FIXED

`queueTransaction` was a bare `db.offline_queue.add()`, and the only handler was a
generic `toast.error("Failed to end transaction")`. `writeWithQuotaRescue()` now
wraps it: on a `QuotaExceededError` it sacrifices what can be rebuilt from the
server — `transactions_cache`, then queued favourite toggles — and retries once,
throwing a distinct `StorageFullError` only if that fails. Both sale paths (POS
quick-end and checkout) now say "Device storage is full — this sale was NOT saved"
instead of a generic failure.

`products_cache` is deliberately NOT sacrificed: it would free the most, but it is
the only thing letting the till sell offline, so dropping it to save one write
would take the whole shop down instead of one row. `offline_queue` is never
touched.

The same wrapper is applied to the product write-through in
`src/lib/products/refresh.ts`, where a quota failure previously surfaced as a
`console.warn` and left the watermark unadvanced — so the app re-pulled the entire
catalogue every cycle, forever, while the cache silently stopped updating.

### Flaky reconnects dead-lettered the entire backlog 🔴 — ✅ FIXED

The most damaging finding. `pushQueuedTransactions` treated **every** failure
identically: a `TypeError: Failed to fetch` counted the same as a `400`.
Connectivity is checked once, at the top of `syncNow()`, and the heartbeat lags up
to 15s. So a link dying at sale 12 of 500 made the remaining 488 fail instantly,
each burning one of its 5 retries, in a fraction of a second — and each reconnect
fires a flush. **Three flaky reconnects dead-lettered every queued sale in the
shop.** The retry cap was sized for permanent rejections (its own comment cites the
P1-3 overflow), not for transport flapping.

Failures are now classified before being recorded:

| Condition | Class | Action |
|---|---|---|
| `fetch` threw — network, DNS, TLS, abort | transient | `retry_count` untouched; flush **stops** |
| `5xx`, `408`, `429` | transient | same |
| other `4xx` | permanent | counts against the budget; dead-letters at 5 |

Stopping the flush on the first transport failure is the important half: the link
is down, so grinding through the rest of the queue is pure damage. The queue is
ordered by `created_at`, so the next flush simply resumes where it stopped.

`SyncHttpError` carries the `Response` to the catch block so classification reads
the status code rather than parsing it back out of a message string.

### Retries were a hot loop 🔴 — ✅ FIXED

`retry_count` was incremented with zero delay; the only spacing was the 30s cycle,
which is per-cycle rather than per-row. Rows now carry `next_attempt_at` and back
off `30s → 1m → 5m → 15m → 1h` with ±20% jitter, so a shop full of devices behind
one router does not retry in lockstep.

**No Dexie version bump.** `next_attempt_at` is not indexed, deliberately:
`getQueuedTransactions()` already reads the whole table and filters in JS, so an
index would buy nothing today, and a schema migration on live devices is real risk
for no gain. When that scan is fixed (deferred item below), index it then.

This split the queue readers, and the distinction matters:

- `getQueuedTransactions()` — "what should the engine send right now" (excludes
  backoff). Used by the flush and the retry interval.
- `getUnsyncedTransactions()` — "what has not reached the server" (includes
  backoff). Used by the History feed and the pending badge. **The History feed was
  switched to this**; leaving it on the former would have made a sale vanish from
  the feed, and drop out of the day's takings, for the length of its backoff.

### Sync reported success while destroying sales 🔴 — ✅ FIXED

`const success = pullResult.success` ignored the push result entirely, so
`SyncIndicator` showed green while the backlog dead-lettered. `success` now
requires `pushResult.failed === 0 && pushResult.deadLettered === 0`.

A flush cut short by the link dropping is *not* an error state — it is this app's
normal condition, the sales are safe, and no retries were spent — so
`abortedOnTransient` keeps the indicator calm while still reporting the work as
outstanding. Only a genuine fault alarms the cashier.

### The product pull blocked the money push 🔴 — ✅ FIXED

`syncNow()` ran `pullProducts()` and the favourites pull *before* the queue flush.
After a multi-day outage the catalogue delta is large, so the money-bearing writes
waited behind a big download on exactly the fragile connection most likely to drop
again mid-flush. Sales that already happened outrank price updates that have not:
the flush now runs first, and products/favourites overlap via `Promise.all`.

### Verified

`typecheck` clean · `lint` at exactly the pre-existing baseline (17 problems on the
four touched library files, byte-identical to the pre-change run; 41 on the two
touched pages, likewise) · production build succeeds · all five `verify-sw` checks
pass.

Behaviour confirmed in a real browser against a production build: `app-shell`
populated with all six routes; **the POS cold-opened with the server fully stopped**,
showing the offline badge, the store, and the cached catalogue with correct LL/USD
prices; client-side navigation to History worked offline; `/api/health` still
returns a live timestamp (i.e. still NetworkOnly, P0-7 intact); the persistence
request ran and recorded its one-time notice.

**Not verified here, and needing the owner's hands:** anything requiring real sales,

### P1-10 🔴→✅ FIXED 2026-08-24 — Offline login produced a session that could never sync

**Found by testing offline login on production.** Offline login itself works well:
the login page detects the outage, shows *"Cached credentials available for
'daoud'"*, relabels the button **Sign In (Offline)**, and
`validateCachedCredentials` authenticates against the cache. Logout correctly
preserves the credential cache (`clearUserFromStorage` says so explicitly), so
a cashier who signs out mid-outage can sign back in.

**But the resulting session was unusable.** Both ONLINE login paths write the
legacy `goldensquirrel_auth` key from inside `login/page.tsx`. The OFFLINE path
never did — `AuthContext.loginOffline` called only `saveUserToStorage`. That key
is the tenancy header for every API call (`sync/engine.ts` sends it as
`x-auth-data`, and many components read `store_id` straight out of it).

Measured on production immediately after an offline login:

```
goldensquirrel_user            present  (daoud, owner, full permissions)
goldensquirrel_auth            ABSENT
x-auth-data the engine sends   {}
GET /api/transactions          401  "Unauthorized - No store_id in auth data"
```

So: a cashier logs in offline during a multi-day outage — the precise scenario
this whole workstream exists for — sells all day, and **not one sale can ever
reach the server.**

**Worse, the offline-survival pass had just made the consequence permanent.**
A 401 is a 4xx, and the new failure classifier counted 4xx against the retry
budget, so every queued sale would have been **dead-lettered after 5 attempts**
instead of merely retrying. The old code would have retried forever and
recovered on the next online login; the new code destroyed the takings.

**Two fixes, both landed:**

1. **Root cause** — `AuthContext.saveLegacyAuthToStorage()` now writes the key,
   called from *both* branches of `loginOffline` (owner and employee). Putting it
   in AuthContext rather than the login page means no future caller can forget it.
2. **Defence in depth** — `isTransientSyncFailure` now treats **401/403 as
   transient**. They say nothing about the sale; they say the caller is not
   currently authenticated, which a re-login fixes. No auth regression should
   ever again be able to dead-letter real money. Genuine payload rejections
   (400/409/422) still count against the budget as intended.

Verified: `typecheck` clean, lint at baseline. The production session left in the
broken state by this test was repaired in place (writing the key restored
`GET /api/transactions` to 200). **Needs a redeploy plus a re-run of the offline
login drill to confirm the fix end-to-end.**

*(Also noted while testing: offline login ignores the `username` field entirely —
`loginOffline(storeUsername, password)` only checks the store username and
password against the single cached credential set. And only ONE set is cached,
last-online-login wins, so an employee who was not the last to authenticate
online cannot log in during an outage. Neither is fixed here.)*

### Full offline drill on production, 2026-08-25

18 minutes fully offline on `goldensquirrel.vercel.app` (store `daoud`, 2,278
products), all API and Supabase traffic blocked at the page, then reconnected.

**Worked, verified end to end:** offline login (via the migrated legacy
credential) · app-shell cold-serves all 5 routes · barcode scanning, cart edits,
duplicate-scan merge · **money rules exact** — `$1.62 × 90,000 = 145,800`, cart
total rounded to `145,000` with the `−800` adjustment shown, applied at the total
and never per line · checkout with **mixed LL + USD** tender: `$2.00 @ 89,000 =
180,000` (return rate, 5k-rounded from 178,000), change `40,000 LL` correct ·
4 sales queued over 18 minutes with **every retry_count still 0 and nothing
dead-lettered** · History offline showed 45 sales (41 cached + 4 queued) with
NOT SYNCED badges and locally-computed totals · Inventory 70 ms with search ·
on reconnect the queue **drained in 20 s, all four timestamps preserved to the
millisecond**, line items intact, and **stock decremented correctly**.

**⚠️ Correction to an in-flight claim.** An apparent "stock never decrements for
offline sales (0/5)" was a MEASUREMENT ERROR, not a bug. `pushSaleInBackground`
calls `decrementCachedStock` at sale time, so a baseline read from
`products_cache` after ringing the sales already contains the decrements.
A clean test against true server state (full re-pull → 4, one offline sale →
sync → full re-pull → 3) confirms the path is correct. Recorded here because the
same trap will catch the next person who tests this.

#### New findings

**1. 🔴 Profit is unavailable offline.** Every other History figure is computed
on-device, but Profit renders `—` because it comes from
`/api/transactions/analytics`. The data is on the device — `products_cache` holds
2,278 products (1,527 with `cost_price`) — but it cannot be joined, because
`CachedTransactionItem` carries only `{id, product_name, quantity, unit_price,
total_price, currency}` and **no `product_id`** (the offline-queue item type does
have one).

Two levels of fix. Cheap: add `product_id` to the cached item and the API's
select, then compute profit locally. Correct: **snapshot `cost_price` onto
`transaction_items` at sale time** — which also fixes a silent historical bug,
since profit for past sales is currently recomputed against each product's
*current* cost, so changing a cost rewrites history. Same class as the
un-stamped exchange rate (P1-7). Needs a migration.

**2. 🔴 Cash register reports "No Shift Open" offline even when a shift exists,
and accepts unlimited duplicate opens.** Offline it cannot read the shift, so it
shows the open-shift prompt. Opening queues a `cash_shift_open` pending write —
but the screen does not change, still shows "No Shift Open" and the same button,
so a cashier will naturally tap it again. Two taps queued two identical writes;
on reconnect both failed `409` (the `UNIQUE (store_id, business_date)` from
migration 021 — a shift already existed), burned all 5 retries and were dropped.
Not corrupting, but it is a dead end with no feedback. Needs an optimistic local
shift state and de-duplication of the queued write.

**3. 🟡 Offline state is per-tab; the sales queue is shared.** A second tab left
open and online drained the offline tab's queue mid-drill — the "offline" tab
kept showing sales as queued while another tab had already pushed them. This is
P2-9's cross-tab concurrency, observed live. Harmless here (the unique
constraint holds), but it means "offline" is not a device-wide state.

**4. 🟡 P1-2 confirmed in live data.** The queued payload for a mixed-currency

valued at 180,000 LL — alongside `amount_paid_usd: 2`. `get_cash_shift_summary`
adds both, so expected LL is overstated by the USD take on every mixed sale.

### Offline profit + cross-tab sync, 2026-08-25

Both raised by the owner after the drill.

**Profit now works offline.** Root cause was the missing join key, not missing
data: the device holds the whole catalogue with cost prices, but
`CachedTransactionItem` carried no `product_id`, so a sold line could not be
traced back to its product. `product_id` now flows through the API select, the
cache type and both History mappings (synced and queued).

The arithmetic itself moved into **`src/lib/analytics/profit.ts`**, and the
analytics route was rewired to use it. That is the important part: two
independent implementations of a money calculation is exactly how this codebase
ended up with four disagreeing LL↔USD conversions (P1-6), so the offline figure
and the server figure now run the *same* function — including its deliberate
"unknown product ⇒ cost = unit_price" fallback, which books an unpriceable line
at zero profit rather than counting its full revenue as profit.

History prefers the server value (it covers the whole range, not just the loaded
page) and falls back to the local calculation when offline or when the request
fails. The local path only prices sales whose lines all resolve to a cached
product — otherwise it shows a dash, because a wrong number on a money screen is
worse than no number. The cost map is built once per store rather than re-read
from IndexedDB on every keystroke.

**Cross-tab sync is now coordinated.** Two changes:

- **`navigator.locks` around the sync run** (`SYNC_LOCK`). `syncInProgress` was
  a per-instance guard while `offline_queue` is shared by every tab, so two tabs
  would each flush the same sales. The unique constraint made that *correct by
  luck* — the loser hits the duplicate branch, which returns early and **skips
  the stock decrement**. Taken with `ifAvailable`, so a second tab skips rather
  than queues: the flush already in progress is doing its work too.
- **`BroadcastChannel` for connectivity.** Status was strictly per-tab, so one
  tab could show "Offline" with sales it believed were queued while a sibling
  had already pushed them — exactly what contaminated the drill. Tabs now share
  probe results, guarded by a freshness check and a "newer than my own probe"
  rule so two tabs cannot flip each other back and forth. Falls back to
  per-tab heartbeats where `BroadcastChannel` is unavailable.

Verified: typecheck clean, lint at exactly the pre-existing baseline (22
problems on the six touched files, unchanged), build green, all five
`verify-sw` checks pass. **Needs a deploy plus a two-tab drill to confirm end
to end.**

### Deferred items, now with production numbers

Measured on a store with **40 total sales** — so none of this is data-volume bound:

| Endpoint / route | Warm timings | Note |
|---|---|---|
| `/api/health` | 195 / 201 / 204 ms | the RTT floor |
| `/api/transactions?limit=50` | 700 / 1251 / **2700** ms | 19 KB |
| `/api/transactions/analytics?dateFilter=all` | 703 / 1526 / 1602 ms (**2888 ms** cold) | 3.2 KB for 40 sales |
| route `/pos/cash` | **2455 ms** to paint | vs 95-107 ms for every other route |

Analytics costs 3.5-8× the baseline round trip to return 3 KB. `/pos/cash` is 25×
slower than its neighbours, matching H3/M8 (three serial round trips, and it
returns the whole day's transaction list that `CashRegisterClient` never reads).
The wild variance points at serverless cold starts plus the per-request Supabase
client (L1/L3).

Console evidence for the render/waste items: `[LocalDB] Cached 40 transactions`
appears **six times** on one History visit (duplicate-fetch finding) ·
`[Supabase Client] Creating client …` repeatedly plus
`Fetch with Restaurant ID: null` on every request — the dead TableMind machinery
(P2-2) still logging in production · **165 synchronous `localStorage` reads for 9
keystrokes** in Inventory search, ~18 per keystroke, one per visible row —
though the measured cost was only 0.2 ms on desktop, so it is latent rather than a
live bottleneck.

Good news: Inventory paints in **77 ms** with 2,278 products (16 DOM rows —
virtualization working), and **zero long tasks** were recorded on any route.
