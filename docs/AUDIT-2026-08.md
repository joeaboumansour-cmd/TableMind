## P0 — Live exposure and live money bugs

### P0-1 🔴 API tenancy is an unsigned client-supplied header

Every data-bearing route reads `store_id` out of a plaintext JSON header and then queries with the **service-role key**, which bypasses RLS entirely.

```ts
// src/app/api/transactions/route.ts:26
const authData = request.headers.get('x-auth-data');
if (!authData) return NextResponse.json({ error: "Unauthorized..." }, { status: 401 });
const parsed = JSON.parse(authData);
store_id = parsed.store_id;
```

There is no signature, no cookie, no session, no JWT check. Anyone can read, write, or delete any store's data:

```
curl -H 'x-auth-data: {"store_id":"<any-uuid>"}' https://<host>/api/transactions
```

**Affected:** `api/transactions/route.ts:26` (GET), `:108` (POST — write into any store), `:285` (DELETE), `api/transactions/analytics/route.ts:70`, `api/cash-shifts/route.ts:58`, `api/cash-adjustments/route.ts:49`.

`src/middleware.ts` → `src/lib/supabase/middleware.ts:40-44` confirms nothing is enforced upstream.

**Fix:** issue a signed session token at login and verify it server-side. The primitive already exists and is imported by nothing: `src/lib/auth/jwt.ts` (`jose`, already a dependency).

### P0-2 🔴 Three API routes have no authentication at all

| Route | Exposure |
|---|---|
| `api/admin/store-users/route.ts` (GET/POST/PATCH/DELETE) | No auth of any kind. `GET ?store_id=X` lists all employees. `POST` creates an employee in **any** store with **arbitrary permissions**. `PATCH` (`:103`) changes any employee's `password_hash`, `permissions`, or `username` by `id` alone — no store scoping. `DELETE ?id=X` removes any employee. Full multi-tenant takeover. |
| `api/products/import/route.ts` | No auth. Service role. With `mode: 'replace_all'` it **deletes all `transaction_items`, all `transactions`, and all `products`** for the supplied `storeId` (`:182-228`). Unauthenticated destruction of a live store's entire sales history. |
| `api/admin/stores/features/route.ts` | No auth. Service role. Anyone can read or flip any store's feature flags and `store_type`. |
| `api/products/export/route.ts` | No auth (audit-log only — lower impact, same class of bug). |

Two **pages** are also unguarded: `src/app/barcodegen/page.tsx` renders unconditionally with no auth gate, and `src/app/admin/transactions/page.tsx:37-48` checks store auth (`goldensquirrel_auth`) while sitting under `/admin`, with none of the `goldensquirrel_admin` check that `admin/page.tsx:131-139` performs.

// src/app/api/cash-adjustments/route.ts:28-30

if (!userId) {

The comment at the top of `cash-shifts/route.ts` claims "We verify server-side (not from client claims) because this feature guards money." The code does the opposite.

### P0-4 🔴 Passwords are plaintext, compared in the browser, and logged

```ts
// src/app/api/admin/login/route.ts:28,39-44
console.log("Login attempt:", { username, password, fetchError, admin });
const isValidPassword = admin.password_hash === password;
console.log("Password comparison:", { storedHash: admin.password_hash, inputPassword: password, isValid: isValidPassword });
```

Both the submitted password and the stored value are written to server logs. The column is named `password_hash` but holds plaintext.

Store-owner login is worse — it happens **client-side**, and the browser fetches the stored credential down to itself:

```ts
// src/app/(auth)/login/page.tsx:90,107
.select("id, username, password_hash, license_expires_at")
if (store.password_hash !== password) { ... }
```

An attacker can retrieve `password_hash` for any username with the public anon key, regardless of the comparison.

And `src/lib/auth/offlineAuth.ts:44-51` caches the **plaintext password** in localStorage for offline login. `cachedAt` is recorded but never checked, so cached credentials never expire; `license_expires_at` is cached but not enforced offline, so offline login bypasses license expiry.

`bcryptjs` is already a dependency and is imported nowhere.

### P0-5 🔴 RLS provides no protection

```sql
-- supabase/migrations/002_admin_rls.sql:7-10
CREATE POLICY "admin_users_select" ON admin_users FOR SELECT USING (true);
CREATE POLICY "admin_users_all"    ON admin_users FOR ALL    USING (true);
```

With the public `NEXT_PUBLIC_SUPABASE_ANON_KEY`, anyone can `SELECT * FROM admin_users` and read every admin's plaintext password, or `INSERT` a new admin. `supabase/seed.sql:11` seeds `admin` / `admin123`.

Same `USING (true)` on all four verbs for `store_users` (which holds `password_hash`), `cash_shifts`, and `cash_adjustments` — `010_store_users.sql:23-26`, `021_cash_management.sql:60-68`.

The "real" policies are simultaneously useless in the other direction: `001_initial_schema.sql:95-98` gates `stores`, `products`, `transactions`, `transaction_items` on `store_id = auth.uid()`. The app never uses Supabase Auth, so `auth.uid()` is always `NULL` and every one of those policies evaluates false. Yet the login page reads `stores` and the sync engine reads `products` with the anon key — meaning **RLS has been disabled or overridden directly in the production database, and the migrations in this repo do not describe the deployed state.** `024_fix_stock_decrement_security.sql:4-8` documents exactly this discovery for the RPC.

`decrement_stock` is `SECURITY DEFINER` with **no `SET search_path`** (`024:39`) — a standard privilege-escalation hazard — and is `GRANT`ed to `anon` (`024:42`). Its `p_store_id DEFAULT NULL` legacy branch (`024:31-37`) lets any anonymous caller decrement stock on any product in any store.

**Before fixing:** dump the *actual* production RLS state. The repo is not a reliable description of it.

## P1 — Money and data correctness

### P1-1 🔴 Offline sales are recorded with the wrong date

`QueuedTransaction` carries `created_at` (`src/lib/db/localDB.ts:68`), but the sync push payload at `src/lib/sync/engine.ts:313-345` never sends it, and `POST /api/transactions` (`:162-186`) never sets it. So `created_at` falls back to the column default `NOW()` — **the moment of sync, not the moment of sale**.

A sale made offline on Friday and synced on Monday is recorded as a Monday sale. This corrupts:
- cash-shift reconciliation, which matches on `created_at::date = v_business_date` (`021_cash_management.sql:106`, `cash-shifts/route.ts:108-109`)
- hourly and day-of-week analytics (`analytics/route.ts:174-190`)
- retention cleanup

**One-line fix, large correctness payoff.** Highest value-per-effort item in this document.

---

### P1-2 🔴 USD payments are double-counted in the cash drawer

Checkout stores `amount_paid` as the LL-equivalent of *everything*, including the USD portion:

```ts
// src/app/checkout/page.tsx:70
const totalPaid = paidLL + convertUsdToLlForReturn(paidUSD);
```

…and separately stores `usd_amount_paid: paidUSD` (`:190`). `get_cash_shift_summary` then adds both:

```sql
-- supabase/migrations/021_cash_management.sql:119-120
(v_opening_ll  + txn_agg.cash_in     - txn_agg.chg     + ...) AS expected_ll,
(v_opening_usd + txn_agg.cash_in_usd - txn_agg.chg_usd + ...) AS expected_usd
```

`cash_in` (`SUM(amount_paid)`) already contains the USD converted at 89,000; `cash_in_usd` contains the same dollars again. **Expected LL is overstated by the USD take on every mixed-currency sale**, and the same double-count applies to change. `perUser` totals share the basis (`cash-shifts/route.ts:129`).

### P1-3 🔴 Money columns overflow at ~1,100 USD

`transactions.subtotal` / `total_amount` / `amount_paid` and `transaction_items.unit_price` / `total_price` are `DECIMAL(10,2)` (`001_initial_schema.sql:54-57,69-70`) — maximum **99,999,999.99**. Amounts are denominated in **LL**, where one item is routinely ~185,000.

A basket over roughly 1,100 USD throws `numeric field overflow`. The POST handler returns 500, and the client treats that as an offline condition and drops the sale into the offline queue — **where it will fail forever on every retry**.

`cash_shifts` was correctly widened to `DECIMAL(12,2)`. `transactions` never was. `products.selling_price` has the same ceiling.

### P1-4 🔴 Sale + line items + stock decrement is not atomic

`src/app/api/transactions/route.ts:229-267` makes three separate round-trips — insert transaction, insert items, loop N× `rpc("decrement_stock")` — with no transaction wrapper. Both failure modes are explicitly swallowed:

```ts
if (itemsError) {
  console.error("Transaction items error:", itemsError);
  // Transaction created but items failed - still return success but log error
}
...
if (stockError) {
  console.error(`[API] Stock decrement failed for product ...`);
  // Don't fail the transaction — log and continue.
}
```

A partial failure produces a header-only sale with no line items (invisible on the receipt, breaks analytics) or un-decremented inventory — and the client is told `201 Created`.

Compounding: the items insert (`:230-239`) **does not persist `unit_price_usd` / `total_price_usd`** even though the client sends them (`engine.ts:342-343`, `checkout/page.tsx:199-200`). `transaction_items` has no such columns. Silent field drop.

**Fix:** one `create_transaction(...)` plpgsql function.

### P1-5 🔴 Stock can go negative; no input validation on any route

There is no stock check anywhere — not in `cartStore.addItem` (`:18-80`), not in `incrementQuantity` (`:111`), not in the API. `001_initial_schema.sql:117` is explicit: `-- Allows stock to go negative — no guard clause`. Two cashiers on two devices will both sell the last unit.

More broadly, **no route validates input**. There is no Zod/Valibot in the project. `POST /api/transactions` writes `body.subtotal`, `body.total_amount`, `body.amount_paid`, `item.quantity`, `item.unit_price` straight to the database with no type, range, or sign checks. A `quantity` of `-1000` is accepted and **increments** stock via `decrement_stock`. `/api/products/import` validates only `Array.isArray(products)` (`:132`) — `ProductImportData` is compile-time only.

### P1-6 🔴 Four different LL↔USD conversion paths disagree

The same conversion is done differently depending on the screen:

| Location | Method |
|---|---|
| `cartStore.ts:44` | `convertLlToUsdForReturn` — 89,000 |
| `TransactionAnalytics.tsx:169` | `convertLlToUsdForSale` — 90,000 |
| `ProductSearchBar.tsx:267` | raw `selling_price * SELL_RATE` — unrounded, bypasses `convertUsdToLl` |
| `products/page.tsx:1036,1038` | `/ RETURN_RATE` one way, `* SELL_RATE` the other — again unrounded |
| `checkout/page.tsx:82-95` | a **blended weighted rate** — a fourth algorithm |

**The same product can show three different USD values on three screens.** Consolidate on the rules in `CLAUDE.md` §3.

### P1-7 🔴 Exchange rates are hardcoded; per-store rate columns are dead

`src/lib/utils/format.ts:7,13` hardcode `SELL_RATE = 90000` / `RETURN_RATE = 89000`, so a rate change requires a code deploy.

Meanwhile `stores.usd_rate_sell` / `usd_rate_return` **already exist** (`004_usd_support.sql:9-11`) along with SQL helpers `get_store_sell_rate` and `convert_ll_to_usd_sale` — none of which are called anywhere in `src/`.

Separately: transactions carry **no rate stamp**, so historical receipts silently re-price when the rate moves. Both should be fixed together — adding per-store rates without stamping transactions makes the historical problem worse.

### P1-8 ✅ FIXED 2026-08-16 — Barcode lookup ignores store scope

`getCachedProductByBarcode` (`src/lib/db/localDB.ts:211-218`) queries by barcode **with no `store_id` filter at all**, and `products_cache` has no compound `[store_id+barcode]` index. On a device that has served two stores, a scan can return the wrong store's product. Consumed by `src/app/pos/page.tsx:51`.

**Fixed:** the function now takes a required `storeId` and queries the new `[store_id+barcode]` compound index added in Dexie schema `version(3)`. Note the function had no live call sites (it was imported but never invoked), so this was latent rather than actively firing.

The backward-compatibility backfill for discount fields is dead code — old persisted carts are loaded unmigrated.

### P2-8 ⚠️ PARTIALLY FIXED 2026-08-16 — Database hygiene

**Fixed (local/Dexie side):** `cacheTransactions` now scopes its delete to the affected `store_id` (it was calling `.clear()`, wiping *every* store's cached history) and wraps delete+insert in a single Dexie transaction. `transactions_cache` gained a `[store_id+created_at]` compound index so `getCachedTransactions` sorts on the index instead of doing an in-memory `.sortBy()` of the whole result set. `decrementCachedStock` batches into one transaction instead of one per cart line. Added `getPendingWritesByType()` so callers stop reading the whole table and filtering in JS.

**Still open (Postgres side):** the retention trigger on the checkout hot path, the duplicate `008` migration number, and the `seedProductsIfNeeded` FK hazard.

#### Original finding

- **Retention trigger on the checkout hot path.** `012_auto_cleanup_trigger.sql:58-64` is an `AFTER INSERT … FOR EACH ROW` trigger on `transactions` that runs `COUNT(*)` over the store's entire transaction table plus up to two `DELETE`s **on every single sale**. At the 5,000-row default this adds a full count scan to checkout latency and creates deadlock potential between concurrent inserts. A scheduled job already exists in `013_scheduled_cleanup.sql`, making the trigger redundant.
- **Duplicate migration number `008`** — both `008_product_groups.sql` and `008_product_variants.sql` exist. Ordering is undefined; `009_revert.sql` then partially undoes `009` and re-adds columns from `008`. Migration history is not reproducible.
- **Non-atomic cache replace.** `cacheTransactions` (`localDB.ts:265-268`) does `clear()` then `bulkAdd()` outside a Dexie transaction. A crash between them leaves the history cache empty.
- **`seedProductsIfNeeded`** (`localDB.ts:392-439`) checks the same condition twice (`:395` and `:402` — dead branch), and remaps seed products' `store_id` to the caller's store **while keeping the seed `id`s**. A sale made before the first reconcile writes `transaction_items.product_id` values that violate the FK to `products(id)` — insert failure, silently swallowed at `route.ts:245-248`.
- **`transactions_cache` sorting** — `getCachedTransactions` (`:271-277`) uses `.sortBy(created_at)`, an in-memory sort of the whole result set. A compound `[store_id+created_at]` index would let Dexie sort on the index.

### P2-9 ⚠️ PARTIALLY FIXED 2026-08-16 — Sync engine rough edges

**Fixed in this pass:**

- **`pullProducts` reconcile was destroying the cache.** Worse than the "expensive" note below: the reconcile ID fetch (`engine.ts:251-254`) had no `.range()`, so PostgREST truncated it at 1000 rows and `reconcileProductsCache` deleted every product past that point. The completeness check then re-pulled the whole catalog, and the next sync deleted them again — **a permanent delete/refetch loop every 30s on any store with >1000 products** (live at the current 2,500). Now uses a paginated `fetchAllProductIds()` and refuses to delete unless the fetched ID count matches the server's exact count. The full ID sweep is also skipped entirely unless the cache is *ahead* of the server. Guard logic extracted as the pure function `evaluateReconcile()` in `src/lib/sync/engine.ts` so it can be reasoned about (and re-tested) in isolation.
- **Retry caps now applied uniformly.** Queued transactions had no cap at all; cash and favourite writes incremented `retry_count` without ever checking it. All three are capped now. Transactions are **dead-lettered, never dropped** — a completed sale whose money was taken must not be silently discarded (`getDeadLetterTransactions()`).
- **`getPendingWrites()` inside the push loop** is hoisted out — it was a full table scan per queued transaction.
- **`visibilitychange` was registered on `window`**, where it does not fire on iOS Safari/WKWebView — the primary POS platform. Moved to `document`.

**Fixed 2026-08-19:**

- **The delta branch was never paginated.** The reconcile ID fetch was fixed on 2026-08-16, but the incremental product select immediately above it kept a bare `.gte("updated_at", …)` with a comment asserting that "no pagination [is] needed for small deltas". A bulk price change across a 2,300-product catalogue is not a small delta: PostgREST returned the first 1000 rows and reported success, leaving the rest of the store priced from stale cache until something else forced a full pull. The `BulkPriceDialog` feature made this reachable in one tap. Now paginated, ordered `updated_at, id` (`updated_at` alone is not unique — a bulk write stamps every row with the same `NOW()`).
- **The watermark had no clock-skew margin.** It is a client-side `Date.now()` compared against a server-side `updated_at`. A device running even slightly fast asked for changes since a moment that had not happened on the server yet, permanently skipping everything written in the gap. The query now rewinds 5 minutes; re-fetching a handful of already-current rows is free and idempotent, missing a price change is not.
- **Two copies of the same algorithm could run at once.** `SyncEngine.pullProducts` and the inventory page's own fetch were near-identical implementations that had drifted on the details that matter, and nothing stopped them racing — entering Inventory fires the engine's `visibilitychange` sync too, so both ran a full pull simultaneously. Both now call `refreshProductsIntoCache()` in `src/lib/products/refresh.ts`, which holds a per-store in-flight promise so the second caller joins the first. `evaluateReconcile()` moved there with it and is re-exported from `engine.ts`.
- **`pullProducts` is no longer expensive per sync** (see the "expensive" note below): the full `select("id")` sweep was already skipped unless the cache is ahead of the server, and the delta select now asks for named columns instead of `select("*")`.

**Still open:** cross-tab concurrency (`syncInProgress` is per-instance), the unrecoverable partial insert (P1-4), the over-broad legacy cleanup matching on `product_id` alone, and exponential backoff (retries are still a flat 30s).

#### Original finding

The core is sound — serial push, `syncInProgress` guard, `UNIQUE (store_id, transaction_number)` with a `23505` fallback, cache reconciliation, retry cap. These issues sit around it:

- **Cross-tab concurrency.** `syncInProgress` is per-instance. Two tabs share one IndexedDB but have separate `syncEngine` singletons; both will read `offline_queue` and both will POST. The unique constraint prevents duplicate transactions, but the second tab hits the duplicate branch (`route.ts:125-157`) which **skips** the stock decrement. Correct by luck, not design.
- **Unrecoverable partial insert.** If the transaction insert succeeds but the items insert fails, the retry hits the duplicate branch and the items are **never written**. See P1-4.
- **Retry caps not applied uniformly.** `processPendingWrites` caps at `MAX_PENDING_WRITE_RETRIES = 5` (`engine.ts:26,490-496`), but `processPendingFavoriteWrites` (`frequentlyUsed.ts:244-289`) increments `retry_count` and **never checks it** — a permanently failing favourite write retries forever every 30s. Cash writes (`engine.ts:469-486`) also increment without checking.
- **Over-broad legacy cleanup.** `engine.ts:371-385` deletes pending stock-decrement writes matching a synced transaction's product IDs — but matches on `product_id` alone, so syncing transaction A can delete a legacy decrement belonging to transaction B for the same product. Narrow window (legacy data only), real effect.
- **`pullProducts` is expensive.** Every sync issues a delta select, a `count: exact` head query, and a **full `select("id")` of every product in the store** for reconciliation (`:251-254`). For a 10k-product store that's 10k rows every 30s while the queue is non-empty.

### P2-15 ✅ FIXED 2026-08-19 — Inventory reloaded itself, and cost 4s to open

Two separate faults, reported together as "the inventory page randomly reloads and takes a while".

**The reload.** `PWAUpdateListener` is the only automatic `window.location.reload()` in the app. It fires on the service-worker `controllerchange` event and was guarded by exactly one condition: the cart is empty. On every screen except the POS the cart is *always* empty, so the guard protected nothing — a cashier part-way through building a bulk selection on Inventory had the page reloaded under them and the selection thrown away. Foregrounding the PWA calls `registration.update()`, and with `skipWaiting` + `clientsClaim` in the generated worker a newly deployed version activates seconds later, which is why it read as "a few seconds after I entered the page". Production only, so `next dev` could never reproduce it.

Fixed by replacing "is the cart empty" with "is anybody mid-task": `src/lib/pwa/reloadGuard.ts` is a hold registry, screens declare their own busy state via `useReloadGuard(active, reason)`, and the update listener defers until every hold clears — retrying on hold release, on the cart emptying, and on the next foreground. The update still applies automatically and silently; it just waits for a safe moment. Holds are registered by Inventory (selection mode, any open dialog, an in-flight submit), Checkout (unconditional), the cash register (any counted-cash dialog) and the POS completion dialogs.

**The 4 seconds.** The page called `fetchProducts(storeId, true)`, and `forceRefresh: true` made `fetchProductsCacheFirst` skip the entire IndexedDB block *including the `onCacheHit` instant-paint callback*. So every entry blocked on three sequential `select("*")` round-trips of 1000 rows, a 2,276-row `bulkPut`, and a full reconcile sweep before rendering anything. The cache is a complete mirror of the catalogue and the POS page already proved the pattern.

Inventory now paints from `getCachedProductsSortedByName()` immediately (name-ordered via the existing `[store_id+name]` index, so the list cannot reshuffle when fresh rows land) and refreshes behind it via `refreshProductsIntoCache()` — still hitting Supabase on every entry, but asking only for rows whose `updated_at` moved. `forceRefresh` is gone as a concept; `fetchProductsCacheFirst` had no other callers and was removed.

Three smaller faults fixed alongside:

- **Offline rendered an empty page.** `fetchProducts` opened with a `connectivity.isOnline` check that toasted "No internet connection" and returned *before* touching the cache — on an offline-first POS holding a complete local catalogue. The cache is now painted first and the toast only fires when there is genuinely nothing to show.
- **The list re-laid-out for no reason.** The refresh unconditionally called `setProducts`, replacing every product object identity and cascading through `filteredProducts` → `listRows` → the virtualiser's re-measure — a visible jump under a selection in progress. `refreshProductsIntoCache` returns a `changed` flag; state is only replaced when the cache actually moved.
- **Nothing cancelled an in-flight load.** The `[user]` effect had no cleanup, so a slow fetch always landed, including into an unmounted page. Loads now carry a token that the effect cleanup invalidates.

**Related look-alike, also fixed:** `useFeatureFlags` resolved from the database 1–3s after mount and could flip a flag under the user. `FEATURE_PRESETS.general.product_discount` is `false` while `FEATURES.product_discount.default` is `true`, and the API returns `data?.features || {}` — which merges to the latter. So on any store with an empty `features` column the flag flipped false → true a second in and mounted a guarded subtree mid-session. The pre-database default now uses `mergeFeaturesWithDefaults({})`, matching exactly what the API produces; the database result is only applied when it differs from what is already shown; and the request is de-duplicated per store, since at least two `useFeatureFlags()` instances are live on the Inventory route and each was issuing its own. (`FEATURE_PRESETS` is unchanged — it is for provisioning a new store from the admin screen, not for guessing at an existing one.)

**Not done, noted:** `019_performance_indexes.sql` creates the `updated_at` trigger as `BEFORE UPDATE` only. Inserts currently rely on the column's `DEFAULT NOW()`, which holds for every insert path in this codebase, but an insert that explicitly passed `updated_at` would be invisible to delta sync. Widening it to `BEFORE INSERT OR UPDATE` is a one-line migration and belongs in its own reviewed change.
